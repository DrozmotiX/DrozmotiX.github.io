Log-Meldungen ​

Was bedeutet die Warnung "State attribute definition missing"? ​

Kurz: Die Meldung ist harmlos, du musst nichts tun. WLED liefert ein Feld, für das der Adapter keine eigene Beschreibung hat. Der Adapter legt den Datenpunkt trotzdem an. Seit v0.7.1 steht die Meldung nur noch auf der Log-Stufe „debug“.

So sieht die Meldung aus:

text
State attribute definition missing for : <Feld> with value : <Wert>

Was dahintersteckt ​

Der Adapter hat eine Liste mit allen WLED-Feldern, die er kennt. Darin steht für jedes Feld der Name, der Datentyp, die Rolle und ob du den Datenpunkt schreiben darfst. Bringt eine neue WLED-Firmware ein Feld mit, das in der Liste fehlt, legt der Adapter den Datenpunkt so an:

  • Der Name ist der Feldname aus WLED.
  • Der Datentyp richtet sich nach dem Wert, den WLED liefert.
  • Der Datenpunkt ist nur lesbar. Schreiben über diesen Datenpunkt geht nicht.

Beispiele aus der Vergangenheit sind cct, n und liveseg. Sie kamen mit neuen WLED-Versionen und stehen inzwischen in der Liste.

Willst du ein solches Feld trotzdem setzen, schickst du es als JSON-Befehl über den Datenpunkt action. Fehlt dir ein Feld dauerhaft, melde es in einem GitHub-Issue.

Ältere Versionen ​

Bis v0.7.0: Die Meldung erschien als Warnung oder Fehler im normalen Log, teils mit dem Zusatz Sentry disabled, error caught. In v0.5.x konnte sich die Instanz danach beenden. Aktualisiere in diesem Fall den Adapter.

Bis v0.9.2: Auf der Stufe „debug“ steht die Meldung bei jeder Aktualisierung des Geräts erneut im Log, immer wieder für dasselbe Feld.

Ab v0.9.3: Der Adapter meldet jedes fehlende Feld nur einmal je Start (#917).

Siehe auch: Wie sende ich einen kompletten JSON-Befehl an WLED aus ioBroker? · Warum funktioniert der Adapter nach einem WLED-Firmware-Update nicht mehr?

Was bedeuten Warnungen zu falschem Datentyp oder fehlendem "val" beim Schreiben von States? ​

Kurz: ioBroker prüft jeden Wert, der in einen Datenpunkt geschrieben wird, gegen dessen Datentyp. Passt der Typ nicht, steht eine Warnung im Log. Kommt sie von deinem Skript, schreibst du den Wert im falschen Typ, zum Beispiel "true" als Text statt true. Kommt sie vom Adapter selbst, hilft ein Update.

So sehen die Meldungen aus:

text
State value to set for "wled.0.<MAC>.<State>" has to be type "boolean" but received type "string"
State value to set for "wled.0.<MAC>.<State>" has to be one of type "string", "number", "boolean" but received type "object"
State value to set is invalid for wled.0.<MAC>.<State>: The state is missing the required property val!

Am Anfang der Log-Zeile steht, wer geschrieben hat. Steht dort wled.<Instanz>, kommt der Wert vom Adapter. Steht dort zum Beispiel javascript.0, kommt er aus deinem Skript.

Welchen Datentyp erwarten die Datenpunkte? ​

DatenpunktTypBeispiel
onWahrheitswert (boolean)true oder false
briZahl0 bis 255
psZahl3 für Preset 3
plZahl1 für Playlist 1
transitionZahl7
seg.<Segment>.col.0, .1, .2Text mit Zahlen in eckigen Klammern"[255,0,0]" oder mit Weißkanal "[255,0,0,0]"
seg.<Segment>.col.0_HEX, .1_HEX, .2_HEXText"#ff0000"
actionText mit JSON{"on":true,"bri":128} als Text
_info._onlineWahrheitswert (boolean), nur lesbartrue oder false

Die Typen von on, bri, ps, pl und transition legt der Adapter beim Anlegen nach dem Wert fest, den WLED liefert. Die Farb-Datenpunkte sind vom Typ „mixed“ und enthalten die Farbe als Text. Beim Schreiben nimmt der Adapter auch "255,0,0" ohne Klammern an.

So schreibst du die Werte im richtigen Typ ​

Im Skript übergibst du Zahlen und Wahrheitswerte ohne Anführungszeichen, Farben als Text:

js
setState('wled.0.<MAC>.on', true);                  // nicht 'true'
setState('wled.0.<MAC>.bri', 128);                  // nicht '128'
setState('wled.0.<MAC>.ps', 3);                     // nicht '3'
setState('wled.0.<MAC>.seg.0.col.0', '[255,0,0]');  // Text, keine Liste
setState('wled.0.<MAC>.seg.0.col.0_HEX', '#ff0000');

In Blockly bestimmt der Block, den du an „steuere“ oder „aktualisiere“ anhängst, den Typ:

  1. Für on nimmst du den Logik-Block „wahr“ oder „falsch“. Ein Text-Block mit true liefert Text.
  2. Für bri, ps und pl nimmst du den Zahl-Block aus „Mathematik“. Ein Text-Block mit 3 liefert Text.
  3. Für Farben nimmst du einen Text-Block mit [255,0,0] oder #ff0000. Ein Listen-Block liefert eine Liste, also den Typ „object“.

Meldungen vom Adapter selbst ​

Bis v0.9.2: Ist ein Gerät nicht erreichbar, schreibt der Adapter _info._online als Text. Im Log steht dann State value to set for "wled.0.<MAC>._info._online" has to be type "boolean" but received type "string". Du musst nichts ändern, die Meldung kommt vom Adapter.

Ab v0.9.3: _info._online ist immer ein Wahrheitswert, die Meldung entfällt (#788, #794).

Die Meldung The state is missing the required property val! und Typ-Meldungen zu Datenpunkten unter _info wie _info.mac kamen von Adapterversionen aus 2020 und 2021. Heute überspringt der Adapter leere Werte. Siehst du diese Meldungen noch, aktualisiere den Adapter.

Datenpunkte, die sich mit v0.9.3 ändern ​

Ab v0.9.3: seg.<Segment>.mi (Segment spiegeln) ist ein Wahrheitswert und lässt sich schreiben (#918).

Ab v0.9.3: time ist eine Zahl (Unix-Zeitstempel) und lässt sich schreiben, um die Uhrzeit des Geräts zu setzen (#919). Bis v0.9.2 ist time vom Typ „mixed“ und nur lesbar.

Was bedeuten die Fehler "Gerät nicht erreichbar" und "WebSocket was closed before the connection was established"? ​

Kurz: Beide Meldungen heißen: Der Adapter erreicht das Gerät gerade nicht. Meist ist das Gerät aus, hat schlechten WLAN-Empfang oder eine neue IP-Adresse, oder es sind schon zu viele Programme per WebSocket mit ihm verbunden. Prüfe zuerst, ob sich die WLED-Oberfläche vom ioBroker-Netz aus öffnen lässt.

Die Meldungen und ihre Ursachen ​

Meldung im LogStufeBedeutungHäufige Ursache
Unable to initialise 192.168.x.y will retry in scheduled interval !WarnungDer Adapter hat das Gerät per HTTP gefragt und keine Antwort bekommen. Er versucht es später erneut.Gerät aus oder ohne Strom, falsche IP-Adresse, WLAN weg
Heartbeat of device 192.168.x.y failed, will try to reconnectWarnungEin Gerät, das schon verbunden war, antwortet bei der regelmäßigen Prüfung nicht mehr.Gerät ausgeschaltet oder neu gestartet, WLAN-Abbruch
Device 192.168.x.y unavailable (attempt 2/5), will retry in 60 secondsInfoZählt die Wiederholungen nach einem Ausfall mit.wie oben
Websocket connection error : Error: WebSocket was closed before the connection was establishedFehlerDer Adapter hat eine WebSocket-Verbindung aufgebaut, aber das Gerät hat sie nicht angenommen, bevor sie wieder geschlossen wurde.Gerät aus oder überlastet, schlechtes WLAN, alle WebSocket-Plätze in WLED belegt
Client 192.168.x.y does not support websocket, please consider upgrading your WLED firmware to >= 0.12. Switching to http-APi !WarnungDie Firmware hat keinen WebSocket. Der Adapter fragt das Gerät nur per HTTP ab.WLED älter als 0.12

Ein Fehler Websocket connection error bedeutet also nicht, dass der Adapter kaputt ist. Er steht auch dann auf der Stufe „Fehler“, wenn das Gerät einfach nur aus ist.

So prüfst du der Reihe nach ​

  1. Öffne http://192.168.x.y im Browser eines Rechners im selben Netz wie ioBroker. Öffnet sich die WLED-Oberfläche nicht, liegt das Problem am Gerät oder im Netz, nicht am Adapter.
  2. Prüfe die WLAN-Signalstärke in WLED unter „Info“ oder in ioBroker unter wled.<Instanz>.<MAC>._info.wifi.signal.
  3. Prüfe wled.<Instanz>.<MAC>._info.ws. Der Wert zeigt, wie viele WebSocket-Verbindungen gerade bestehen. Ein ESP8266 hält höchstens 3, ein ESP32 höchstens 8. Schließ WLED-Oberflächen und Apps, die du nicht brauchst.
  4. Hat das Gerät eine neue IP-Adresse bekommen, gib ihm im Router eine feste Adresse und lass den Adapter es neu finden.
  5. Liegen ioBroker und WLED in getrennten Netzen (VLAN), muss die Verbindung von ioBroker zu WLED auf Port 80 erlaubt sein.

In der Gerätetabelle der Instanzeinstellungen steht ein Gerät, das nicht antwortet, auf rot. Grün heißt, _info._online ist true.

Ab v0.9.3: Ein Ausfall steht nur noch einmal als Warnung im Log. Die Zeilen Device … unavailable (attempt …) und weitere Unable to initialise … stehen auf der Stufe „debug“ (#903, #788). Antwortet eine IP-Adresse, die du von Hand hinzufügen willst, nicht, steht Unable to initialise 192.168.x.y, device does not respond im Log.

Ab v0.9.3: Schreibst du einen Befehl an ein Gerät, das offline ist, steht Device <MAC> (192.168.x.y) is offline, command for <State> discarded als Warnung im Log (#904).

Was sind die Sentry-Meldungen im Log? ​

Kurz: Sentry ist ein Dienst, über den der Adapter Programmfehler an den Entwickler meldet, damit sie behoben werden können. Die Sentry-Zeilen im Log gehören immer zu einer Fehlermeldung direkt davor, es ist derselbe Fehler. Abschalten kannst du Sentry nur über ioBroker selbst, für den ganzen Host oder für eine Instanz, nicht in den Einstellungen des Adapters.

Was gemeldet wird ​

Fängt der Adapter einen Programmfehler ab, schreibt er ihn ins Log und gibt ihn an das Sentry-Plugin von ioBroker weiter. Gemeldet wird die Fehlermeldung mit der Stelle im Code, also dasselbe, was auch im Log steht. Hast du ioBroker erlaubt, Diagnosedaten zu senden, kommt eine anonyme Kennung deiner Installation dazu, ohne Namen oder E-Mail-Adresse. Fehlende Datenpunkt-Beschreibungen meldet der Adapter seit v0.6.6 nicht mehr.

NOTE

Die README nennt als gemeldete Inhalte auch „new device schemas“. Das stimmt seit v0.6.6 nicht mehr.

Die Meldungen im Log ​

Bis v0.9.2 steht jeder abgefangene Fehler zweimal im Log, zuerst als Fehler mit der Stelle im Code, zum Beispiel [watchDog] TypeError: …, und direkt danach eine der beiden Zeilen:

ZeileStufeBedeutung
[Error caught and sent to Sentry, thank you for collaborating!] <Fehler>InfoSentry ist aktiv, der Fehler wurde gemeldet.
Sentry disabled, error caught : <Fehler>FehlerSentry ist abgeschaltet, gemeldet wurde nichts. Die Zeile wiederholt nur den Fehler davor.

Werte nur die erste Zeile aus. Um die Ursache zu finden, hilft die Seite Warum startet der Adapter nach einem Update nicht oder reagiert nicht mehr?

Ab v0.9.3: Jeder Fehler steht nur einmal im Log. Die Übergabe an Sentry steht auf der Stufe „debug“: Error sent to Sentry: <Fehler> oder Sentry disabled, error not sent: <Fehler> (#913). Ein Befehl an ein Gerät, das offline ist, ist kein Programmfehler mehr und geht nicht mehr an Sentry (#904).

So schaltest du Sentry ab ​

Sentry ist ein Plugin von ioBroker, nicht vom WLED-Adapter. Du schaltest es auf der Konsole des ioBroker-Hosts ab:

  • nur für den WLED-Adapter: iobroker plugin disable sentry --instance wled.0
  • für den ganzen Host: iobroker plugin disable sentry

Alternativ setzt du den Datenpunkt system.adapter.wled.0.plugins.sentry.enabled auf false. Im Log der Instanz steht danach eine Meldung, dass Sentry abgeschaltet ist. Mehr dazu in der Beschreibung des Sentry-Plugins.

TIP

Lass Sentry eingeschaltet, wenn es für dich in Ordnung ist. Fehler, die nicht gemeldet werden, findet der Entwickler nur, wenn du sie selbst in einem GitHub-Issue meldest.
